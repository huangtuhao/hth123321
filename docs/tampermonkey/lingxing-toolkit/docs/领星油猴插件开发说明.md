# 领星油猴插件开发说明

这份文档供 Codex、WorkBuddy 和其他 AI 使用。当领星 MCP、正式 API 和已经登记的本地数据都不能完成任务时，使用这里的流程，不要从零猜测领星接口或认证方法。

## 一句话路由规则

当任务缺少领星数据或网页操作能力时：先检查本地目录、已有采集器和已登记 job capability；有实时刷新能力时由 AI 通过桥 CLI 创建任务并等待结果；没有能力时才让用户用“领星ERP-接口探针”记录一次真实操作；读取脱敏样本后，复制功能模板并显式选择正确的领星页面请求方法；生成独立、最小权限的油猴插件，由用户安装测试；数据成功落地后继续完成原任务。

## 第一步：判断是否真的需要网页旁路

按顺序检查：

1. 领星 MCP 是否已有完整资源；
2. `catalog.json` 是否已有相应 Dataset、配置或采集器；
3. 已有数据是否足够新且 manifest 显示成功、完整；
4. 如果数据需要刷新，是否已有相应 job capability；
5. 只有上述能力确实缺失时，才进入探针流程。

临时网络失败、参数错误或 MCP 授权失效不是“能力缺失”，应先诊断原链路。

### 已有 capability 时直接刷新

从 `catalog.json` 读取实际 `cli_path`，先列出任务能力：

```powershell
node <cli_path> job list-capabilities
```

例如 FBA 货件已经登记为：

```powershell
node <cli_path> job run lingxing.fba_shipments.refresh --wait
```

运行时必须有一个安装了对应正式插件的领星页面已打开并登录，插件也已完成桥接配对。桥不能启动或登录浏览器。只有任务进入 `succeeded`，并且 `C:\数据\领星\manifest.json` 中 `datasets.fba_shipments` 指向的正式快照通过完整性检查，才能使用新数据；job result 只是运行摘要，`pending`、CLI 等待超时、`failed` 和 `expired` 都不是成功。

能力列表没有目标 ID 时，不要让 AI 临时传入 endpoint 或原始 payload。应继续下面的探针流程，开发并验证一个窄的正式业务插件，再决定是否登记 capability。

### 领星自动化中心与运行状态

`1.1.0` 起，原“领星ERP-接口探针”同时是公共状态中心。它默认只显示可拖动、可贴边的收起状态条，按逻辑功能去重显示在线数、运行中和异常数。展开后可看每个已登记功能的页面实例、最后心跳和 capability。点击 `×` 会完全隐藏；需要恢复时，从油猴菜单唯一入口“领星自动化中心：显示状态栏”打开。

- `/health.runtime_summary` 是匿名汇总，所以探针尚未配对时仍能区分“桥离线”与“桥在线”；
- 每个功能的明细来自 `GET /v2/runtime/status`，需要该中心客户端拥有 `runtime:read` 权限；
- 旧业务插件不会因为升级中心就自动出现。它们需要更新一次，用独立 `instance_id` 定期调用 SDK `heartbeat(instanceId, { state, version, message })`；
- 默认每 20 秒发送一次，桥端 TTL 为 90 秒；同一功能打开多个标签页时会按 `client_id` 聚合成一个在线功能；
- 心跳请求严格只允许 `instance_id / state / version / message`，状态只允许 `idle / running / error`。不要上传账号、URL、请求参数、capability 或 job ID；身份、能力和当前任务由桥端推导；
- 状态中心只读状态，不领取 job，也不替代每个正式插件的业务执行链。

## 第二步：取得真实请求证据

用户操作：

1. 安装并启用 `领星ERP-接口探针.user.js`；
2. 打开目标领星页面，展开页面边缘的“领星自动化中心”状态条；
3. 展开默认关闭的“接口探针（高级工具）”，填写样本说明；
4. 点击“开始记录”；
5. 在领星页面只完成一次目标操作，例如查询、切换到下一页或下载；
6. 点击“停止”，取消无关请求的勾选；
7. 第一次使用先“桥接配对”，然后“保存到本地”。桥不可用时可下载 JSON。

除“显示状态栏”外，开始、停止、清空、配对、选择请求和保存都在高级工具区内完成，不应再向油猴菜单添加这些操作。公共状态中心常驻时不会安装网络请求 hook；只有首次手动点击“开始记录”时才会安装。

探针的配对码由本机命令生成，只使用一次：

```powershell
node C:\代码\hth123321\docs\local-automation-bridge\bridge-cli.cjs client pair-code userscript.lingxing.request-probe.v1
```

样本保存到 `接口样本\领星`。探针会同时尽量记录：

- 逻辑层：调用的是 `post`、`gwPost`、`gateGet` 还是 `gatePost`，以及原始 path、payload、请求分组和结果结构；
- 网络层：最终 URL、方法、状态码和脱敏响应结构。

探针不会自动翻页、重放请求或写正式业务数据。样本也不能被当成完整业务快照。

初版网络层只覆盖当前顶层页面里的 XHR/fetch，以及 `erp.lingxing.com`、`gw.lingxingerp.com` 两个已确认域名；不声称覆盖 Worker、WebSocket、`sendBeacon`、iframe 或浏览器原生下载。逻辑层标记属于 best-effort：只有实际观察到的方法才会写入；没有记录到时不能根据 URL 反推成确定事实。

## 第三步：选择正确的领星请求方法

必须依据逻辑层证据显式选择，禁止自动试错和相互回退：

| 模板方法 | 页面内部方法 | 常见用途 | 关键参数 |
|---|---|---|---|
| `client.post(path, payload, options)` | `$post` | ERP 业务接口 | 某些接口必须带 `sequenceGroup` |
| `client.gwPost(path, payload)` | `$gwPost` | 网关业务接口 | 不能拿来替代 `$post` |
| `client.gateGet(path, config)` | `$gateAxios.get` | GET、文件或网关接口 | config 可包含 `responseType` |
| `client.gatePost(path, payload, config)` | `$gateAxios.post` | POST、文件或网关接口 | config 可包含 `responseType` |

已验证例子：FBA 货件列表 `/api/fba_shipment/showShipment_v2` 使用 `$post`，并传 `fbaCargo` 请求分组。若擅自改用 `$gwPost`，会走到错误网关。

SDK 的边界：

- 查找并等待当前 SPA 页面上的 Vue 请求客户端；
- 保持原方法的 `this`；
- 明确诊断缺失的 transport；
- SPA 更新后可重新发现客户端；
- 不读取或复制领星 Cookie、Token；
- 不使用裸 `fetch`、`GM_xmlhttpRequest` 代替领星内部认证链路；
- 不在方法之间自动回退。

## 第四步：从模板创建独立业务插件

复制 `领星ERP-功能插件模板.user.js`，不要直接修改模板原件，也不要把新功能塞进已稳定的 FBA 大脚本。

必须完成：

1. 改名、版本号和描述；
2. 把 `@match` 收窄到能满足功能的站点范围；
3. 为页面路径实现严格的 `page.test`；
4. 从探针证据填写 `transport`、`path`、`sequenceGroup` 和 payload；
5. 为业务登记独立 bridge client 和最小权限；
6. 验证返回结构、账号身份、筛选范围、稳定主键和总数；
7. 只有全部配置完成后才把 `setupComplete` 改为 `true`；
8. 同步修改 `FEATURE.version`，保留模板内置的 runtime heartbeat，并让手动、自动和 job 三种入口共用 `idle / running / error` 状态；
9. 保持 SDK 内嵌，不增加远程 `@require`。

模板默认 `setupComplete: false`，所以未完成的文件不会误发领星请求或本地桥心跳。模板不会新增常驻业务面板；运行状态统一交给“领星自动化中心”显示。

## 数据采集必须补齐的正确性条件

如果是列表或增量采集，不能只把“请求成功”当成完成。至少要验证：

- 使用稳定排序；
- 每页总数在本轮抓取期间保持一致；
- 到达总数前不能出现空页；
- 主键去重后数量与总数一致；
- 多页完成后重新校验第一页，防止抓取期间列表变化；
- 账号标识来自真实页面或响应，不能写一个所有账号共用的常量；
- 筛选条件生成独立 `scopeFingerprint`；
- 筛选结果绝不能覆盖完整基线；
- 只有桥返回成功确认后，UI 才显示“已保存”。

写操作与只读操作必须分开：只读请求可做有限重试；改名、创建、删除等写操作默认不自动重试，并需要用户明确触发和结果确认。

## 桥接资源设计

按用途选择：

- `dataset`：结构固定、需要快照或增量管理的业务记录；
- `config`：由本地工具维护、浏览器插件读取的小型配置；
- `artifact`：PDF、Excel、ZIP、JSON 证据等文件。

每个正式功能应使用独立客户端 ID，只获得自身需要的资源权限。不要复用探针客户端写正式业务数据；探针客户端只能写接口样本桶。

## 让 AI 主动触发：job capability

只有手动执行已经稳定的正式业务功能，才适合增加任务 worker。worker 不是第二套采集实现，而是同一业务函数的另一个触发入口：

```text
AI/WorkBuddy -> bridge job -> 油猴 worker -> 已验证的 runOnce/采集函数
             <- 状态与摘要 <- Dataset/Artifact 严格 ACK 后完成
```

开发时必须遵守：

1. capability ID 表达固定业务语义，例如 `lingxing.products.refresh`，不能做成 `lingxing.request` 或 `run_anything`；
2. 在桥注册表中单独定义 create/read/execute 权限、`read_only`、确认策略、TTL、输入和结果大小；
3. 浏览器插件只领取自己获权执行的 capability，并在代码中写死 capability 到业务函数的映射；
4. 禁止从任务输入接受 URL、领星 endpoint、原始认证头、任意 payload、JavaScript 或本地路径；
5. 手动和任务运行必须共用分页、完整性、账号、scope、增量基线、单飞锁和桥 ACK 逻辑；
6. 长任务持续报告 progress 续约；断线重领时使用稳定 run ID/幂等语义，不能重复推进基线；
7. 完整数据继续写 Dataset/Artifact，job result 只放运行 ID、账号、记录数、变化摘要和正式文件位置；
8. 只有业务数据落地且基线安全提交后才能报告 `succeeded`；登录、transport、完整性或桥接任一步失败都报告结构化 `failed`；
9. 写入领星状态的能力必须单独登记并要求显式确认，不得混入只读 refresh；
10. 接口探针永远不领取任务。

浏览器页面关闭、电脑休眠或登录过期时，worker 无法运行。这是预期边界，不应通过复制 Cookie、开放任意请求代理或让 AI 登录用户后台来规避。

## 交付与测试清单

AI 交付前至少完成：

- JavaScript 语法检查；
- 页面请求 SDK 的传输分发测试；
- 桥 registry 检查；
- 确认没有裸认证信息和全站 `@match`；
- 用户在已登录页面手动测试一次；
- 检查桥 ACK、manifest、记录数和样本字段；
- 明确自动运行条件及失败提示；
- 如果提供 job capability，验证创建、长轮询领取、progress 续约、完成、TTL、lease 到期重领和幂等键；
- 已配对后验证公共状态中心能看到该功能，手动/自动/job 执行时状态能在约 20 秒内变为“运行中”，失败时显示“异常”，关闭全部相关页面后 90 秒内离线；
- 验证浏览器关闭、页面未登录时不会误报成功，也不会损坏上一次成功数据；
- 数据打通后回到用户最初的分析或业务目标。

## 不要做的事

- 不要从 HAR 中复制 Cookie、Authorization、Auth-Token 等到源码；
- 不要猜 `$post` 和 `$gwPost` 可以互换；
- 不要让一个公共油猴脚本向页面暴露超级请求或任意本地文件能力；
- 不要把任务队列做成任意 endpoint/payload/脚本执行器；
- 不要给接口探针授予 job execute 权限；
- 不要让多个 AI 直接往同一个已上线大脚本追加无关功能；
- 不要把探针样本、当前筛选页或 20 条第一页当成完整数据；
- 不要把“插件代码已生成”当成任务完成，必须验证真实落地结果。

## 正式参考实现：FBA 货件增量导出助手

新建领星采集插件前，AI 应先阅读：

```text
C:\代码\hth123321\docs\tampermonkey\领星ERP-FBA货件数据增量导出助手.user.js
```

它是已运行验证的端到端参考实现，但不是公共宿主。应按职责阅读并迁移模式：

1. **页面请求适配器**：学习如何从 Vue 实例取得并保持原接收者调用 `$post`，以及货件列表为何使用 `vm.$post(path, payload, {}, null, null, "fbaCargo")`，而不是 `$gwPost` 或裸 `fetch`。
2. **分页完整性**：学习固定排序、逐页 `offset/length`、总数在本轮保持一致、空页提前结束保护、稳定主键去重，以及多页后复查第一页来发现抓取期间的位移。
3. **账号与范围**：学习从真实结果推导 `accountKey`、按账号隔离基线，以及用 `QUERY_SCOPE` 约束基线兼容性；新插件若允许筛选，必须生成独立 `scopeFingerprint`，不能用筛选结果覆盖全量基线。
4. **增量基线**：学习 IndexedDB 基线、schema/normalizer 版本、稳定归一化、异常数量下降保护，以及首次全量与后续差异的区分。
5. **桥接提交**：学习固定 client/dataset 的能力边界、健康检查与配对、严格校验 ACK、先写 pending outbox 再提交、只有桥确认写入后才原子推进基线，以及失败后的幂等重发。该脚本使用的是已上线的固定协议封装；新插件应优先使用当前模板和桥 SDK 的 `capabilities` 检查，不要复制旧桥请求代码。
6. **运行控制**：学习跨标签运行锁、锁续期与所有权校验、旧 outbox 优先恢复、每日调度与手动运行共用同一执行链，以及 UI 中运行状态、失败原因、待重发和最后成功时间的呈现。
7. **实时任务 worker**：`lingxing.fba_shipments.refresh` 是首个只读浏览器任务参考。学习如何让 worker 只负责领取和触发，复用与手动运行相同的完整采集链；以及为什么只有严格 ingest ACK、基线提交和运行摘要都完成后，任务才能成功。不要照搬它的 capability ID、账户判定或结果字段到其他业务。

不得照搬 FBA 专属内容，包括：

- `/api/fba_shipment/showShipment_v2`、`fbaCargo` 和货件查询 payload；
- FBA 的筛选、日期、排序、字段名、稳定主键组成、忽略字段和数组归一化规则；
- `PAGE_SIZE`、`MAX_PAGES`、异常降幅、重试间隔、锁时长等阈值；
- `fba_shipments`、客户端 ID、令牌键、保存目录、账号推导字段和每日运行时间。

这些内容必须由新功能的探针证据、接口语义、数据规模和桥 registry 单独确定。可继续参考 `领星ERP-FBA综合发货助手.user.js` 中已经验证的 `$gwPost`、`$gateAxios` 与文件响应调用方式，但同样不能照搬其 endpoint、payload 或业务字段。
