# 本地自动化桥：技术接入说明

这份文档供需要实现浏览器客户端、注册资源、发布配置或排查桥接问题的智能体和开发者使用。若尚未确认是否需要旁路，请先阅读 [AI网页能力旁路-使用说明.md](AI网页能力旁路-使用说明.md)。

## 最重要的判断

- **本地 AI 或脚本能访问文件**：直接读取登记好的业务目录；需要统一校验、版本和原子发布时使用 `bridge-cli.cjs`。
- **浏览器脚本不能直接访问文件**：通过本地桥 v2 API 使用明确授权的资源。
- **AI 需要浏览器实时刷新**：仅在注册表已有对应 job capability 时用 CLI 创建任务，由在线的正式油猴插件领取执行。
- **分析现有 FBA 数据**：直接读取 `C:\数据\领星` 下的 manifest 和快照，不要为了分析而驱动浏览器重新抓取，除非用户明确要求刷新。

桥不是 MCP，也不是所有工具必须经过的总线。它既是浏览器等受限客户端进入少量本地资源的受控入口，也是本地工具向在线浏览器提交固定任务的短期队列；本地文件仍是跨工具共享、长期保存的事实来源。

## 发现入口与当前资源

首先读取：

```text
C:\数据\业务自动化\catalog.json
```

catalog 会给出当前机器上的 `cli_path`、`registry_path`、`sdk_path`、示例和已登记资源路径。不要假定模块安装在固定代码目录，也不要递归扫描整个 `C:\数据`。

| 内容 | 默认位置 | 读取原则 |
| --- | --- | --- |
| 领星 FBA 数据 | `C:\数据\领星\FBA数据` | 先看 `C:\数据\领星\manifest.json` |
| 通用共享配置和文件 | `C:\数据\业务自动化` | 先看 `catalog.json` 和 `_说明` |
| 桥运行状态和 v2 令牌 | 当前用户的应用状态目录 | 不读取、不展示、不上传 |

为兼容旧系统，`C:\数据\领星\_config\bridge-token.txt` 可能暂时存在。它属于秘密文件，不是业务数据源，新功能不得使用。

## 资源模型

v2 只允许访问注册表中预先登记的资源，不接受任意磁盘路径。

### Dataset

浏览器采集后形成的结构化数据。每个数据集有固定 ID、适配器、目标位置、大小限制和允许写入的客户端。

当前 FBA 数据集 ID：

```text
fba_shipments
```

新增数据类型时不能只在注册表里随意增加一个 ID，也不能复用不匹配的 FBA 适配器。应为新数据集明确：

- 数据用途和生产者；
- schema、稳定记录主键和必要字段；
- 分页完成与完整性判断；
- manifest、快照、增量或覆盖策略；
- 大小限制、失败语义和幂等规则；
- 专用适配器及其测试；
- 哪些客户端拥有写权限。

当前代码只内置 `fba_shipments_v1` 适配器；其他数据集需要实现并注册相应适配器，不能假定任意 JSON 都会被接收。

### Config

供客户端读取的版本化 JSON 业务配置，例如货代渠道报价、命名规则或店铺映射。

- 本地工具可生成源 JSON，再用 CLI 发布；
- 浏览器客户端通常只有读权限；
- 只有 ACL 明确允许时，浏览器客户端才能发布；
- 配置 ID 与磁盘路径不同，客户端只应知道 ID。

### Artifact

浏览器产生的 PDF、Excel、箱唛、发票等文件。上传时使用登记好的文件桶 ID；客户端建议文件名，最终目录和清理规则由桥决定。

Artifact 不是任意文件系统写接口。客户端不能提交目录路径，也不能覆盖桶外文件。

### Job capability 与 Job

`job capability` 是注册表中预先登记的浏览器动作，例如：

```text
lingxing.fba_shipments.refresh
```

它描述一个固定业务语义，而不是一个可由调用者自由填写 URL、endpoint、payload 或 JavaScript 的通用代理。每个 capability 至少应定义：

- 稳定 ID 和人类可读名称；
- 哪些客户端可以创建、读取和执行；
- `read_only` 风险等级，以及是否要求显式确认；
- 输入和结果的最大大小；
- 默认/最大 TTL、执行租约和进度续约规则；
- 输入结构、成功结果结构和可预期错误；
- 最终业务结果写入哪个 Dataset、Config 或 Artifact。

`job` 是 capability 的一次短期执行记录，典型生命周期为：

```text
pending -> running -> succeeded
                   -> failed
pending/running    -> expired
```

浏览器通过长轮询领取任务。领取后获得有时限的 lease；执行期间用 progress 续约，异常断开且 lease 到期后任务可以按桥规则重新领取。任务支持 `idempotency_key`：同一次业务意图因 CLI/网络不确定而重试时复用同一键；已经进入终态后若确实要发起新一轮刷新，应使用新键或省略该参数。不要把一个常量键用于每天的所有运行。

Job 不是长期业务数据库。任务结果应只放运行摘要、正式数据位置、记录数和错误；完整记录仍通过资源接口落地。AI 只有看到 `succeeded` 且正式 manifest/桥 ACK 可核对时，才能报告刷新成功。

### Runtime presence 与公共状态中心

Runtime presence 只表示某个已登记浏览器客户端最近是否在线，以及它当前是 `idle`、`running` 还是 `error`；它不是审计日志，也不是业务结果来源。

- 业务插件使用自己的认证令牌调用 `POST /v2/runtime/heartbeat`；
- 请求体严格只允许 `instance_id / state / version / message`；
- `instance_id` 应在每个页面标签生命周期内唯一并保持稳定；建议每 20 秒发送一次；
- 桥端默认 TTL 为 90 秒，过期自动离线，不需要 unload 注销请求；
- 客户端身份、名称、capability 从注册表和认证身份推导；当前 job 从服务端 claim/progress/complete 推导；
- 多标签页按客户端聚合为一个逻辑功能，任一实例 `running` 时整体为 `running`，否则 `error` 优先于 `idle`；
- 公共状态中心使用带 `runtime:read` 权限的独立客户端读取 `GET /v2/runtime/status`；未配对时只能读取 `/health.runtime_summary` 匿名计数。

状态中心不可借 `runtime:read` 获得业务数据、任务执行权或任意页面控制能力。心跳失败也不得阻断业务采集；业务插件应限频记录警告并继续原流程。

## 分析 HAR 和网站请求

HAR 只用于识别业务接口，不是凭据来源。分析时应确认：

1. 请求 URL、方法、业务载荷和必要的业务请求头；
2. 哪些认证信息由当前登录页面自动提供，禁止复制进源码；
3. 页码、offset、limit、总数和最大分页大小；
4. 返回记录数组、总数、错误码和完成条件；
5. 稳定主键以及字段类型是否会变化；
6. 筛选时间范围、排序和可能导致漏数的条件；
7. 请求是否只读，是否会改变网站状态。

优先复用页面现有请求封装，例如网站已经提供且验证可用的请求函数；不要硬编码短期 Token。对 HAR、控制台截图和日志进行最小化处理，不在交付物中保留 Cookie、Auth Token 或完整敏感请求头。

## 新浏览器采集功能的实现顺序

1. 在 `catalog.json` 中确认没有可复用资源。
2. 根据真实请求确定数据结构、完整性和更新语义。
3. 为数据集实现专用适配器及测试。
4. 在注册表中登记资源、独立客户端、允许来源和最小权限。
5. 基于 SDK 和油猴模板生成最终脚本。
6. 保留模板的 runtime heartbeat，让手动、自动和 job 入口共用 `idle / running / error` 状态；不要为每个业务插件再做常驻状态面板。
7. 检查注册表并重启桥，使新能力生效。
8. 为客户端生成一次性配对码，由用户在插件中完成配对。
9. 用户在已登录的目标页面手动执行首次测试。
10. 同时验证网页端成功提示、桥 ACK、manifest、记录数、实际文件和公共状态中心显示。
11. 若该功能需要由 AI 主动刷新，再登记最小 job capability，并让手动运行和 worker 共用同一条经过验证的执行链。
12. 分别测试任务创建、领取、续约、完成、TTL 到期、断线重领和重复幂等键。
13. 把资源和 capability 加入 catalog 后，回到原业务任务使用数据。

如果只需要下载文件，应优先使用专用 artifact 桶；如果浏览器需要读取本地业务规则，应使用只读 config；不要为了省事把所有内容都塞进一个 dataset。

## 生成油猴客户端

新脚本统一使用 v2，客户端 ID 应稳定并带命名空间，例如：

```text
userscript.lingxing.products.v1
userscript.example.invoice-export.v1
```

优先复用 catalog 登记的 `sdk_path` 和 `examples.userscript_template`，把客户端封装源码内嵌进最终用户脚本；不要通过远程 `@require` 动态加载。

脚本必须做到：

1. `@match` 只覆盖实际业务网站，不使用全站通配符；
2. `@connect` 只允许 `127.0.0.1` 及确有需要的本地桥地址；
3. 使用 `GM_xmlhttpRequest` 或等价油猴能力访问本地桥；
4. 首次由用户输入一次性配对码，调用 `POST /v2/pair`；
5. 客户端令牌只保存在该脚本自己的油猴存储中；
6. 后续请求携带客户端 ID 和 Bearer Token；
7. 启动功能前调用 `GET /v2/capabilities`，只显示实际授权功能；
8. 遇到 `401` 或 `403` 时停止敏感操作并提示重新配对或检查权限，不循环猜测令牌；
9. 只有收到成功确认后才显示写入成功；
10. 在协议支持时使用稳定运行 ID 或幂等标识。

实现任务 worker 时还必须做到：

1. 只领取注册表明确授予该客户端执行权限的 capability；
2. 由插件写死 capability 到实际业务执行器的映射，不执行任务输入中的代码、URL、endpoint 或本地路径；
3. 长轮询失败时有限退避，不能高频轰击本地桥；
4. 领取后定期 progress 续约，并在进度中只写非敏感摘要；
5. 手动运行和任务运行调用同一业务函数、同一分页完整性检查和同一桥接提交逻辑；
6. 只有 Dataset/Artifact 获得严格成功 ACK 且本地基线已安全推进后，才 `complete` 为成功；
7. 把登录失效、页面 transport 不存在、接口错误、完整性失败和桥写入失败转换为可诊断的失败结果；
8. 对网页写操作在执行前验证显式确认标记；只读能力不得暗含改名、创建、删除或提交等副作用。

认证请求头：

```http
X-Local-Bridge-Client: <clientId>
Authorization: Bearer <clientToken>
```

桥接配对只授权本地资源，不授权网站账号。调用网站接口仍依赖用户当前页面的合法登录状态和权限。

## v2 接口速查

| 接口 | 作用 | 关键限制 |
| --- | --- | --- |
| `GET /health` | 检查本地服务 | 不代表某客户端拥有资源权限 |
| `POST /v2/pair` | 一次性配对 | 必须使用已登记客户端和有效配对码 |
| `GET /v2/capabilities` | 获取当前权限 | 客户端应以结果驱动界面和功能 |
| `POST /v2/datasets/{id}/ingest` | 写数据集 | 需写权限并满足专用适配器校验 |
| `GET /v2/configs/{id}` | 读取配置 | 需该配置读权限 |
| `PUT /v2/configs/{id}` | 发布配置 | 需写权限；浏览器默认不应拥有 |
| `POST /v2/artifacts/{bucket}?filename=...` | 上传文件 | 需桶写权限；文件名必须 URL 编码 |
| `GET /v2/job-capabilities` | 列出当前客户端可见任务能力 | 本地 CLI 可列出全部公开能力；浏览器只看到获授权能力 |
| `POST /v2/jobs` | 创建任务 | 只能使用已登记 capability；受输入、TTL、确认和幂等规则约束 |
| `POST /v2/jobs/claim` | 长轮询领取任务 | 仅执行客户端；返回 lease，不能领取越权能力 |
| `GET /v2/jobs/{id}` | 查询任务 | 仅创建者、执行者或受信任本机 CLI 可读 |
| `POST /v2/jobs/{id}/progress` | 报告进度并续约 | 必须提供当前 lease；进度不得包含秘密或完整大数据 |
| `POST /v2/jobs/{id}/complete` | 提交成功或失败终态 | 必须提供当前 lease；终态不可被旧 lease 覆盖 |
| `POST /v2/runtime/heartbeat` | 上报浏览器实例运行状态 | 仅四个允许字段；身份、能力和当前 job 由服务端推导 |
| `GET /v2/runtime/status` | 读取逻辑客户端和实例状态 | 需要 `runtime:read`；普通业务客户端不应申请 |

具体载荷、限制和响应字段以当前资源协议与 `capabilities` 为准。不要根据资源 ID 推测磁盘路径，也不要自行降级到 v1。

## CLI、注册表与重启

从 catalog 读取实际 `cli_path` 后可使用：

```powershell
node bridge-cli.cjs health
node bridge-cli.cjs registry check
node bridge-cli.cjs client pair-code <client-id>
node bridge-cli.cjs config list
node bridge-cli.cjs config get <config-id>
node bridge-cli.cjs config publish <config-id> <json-file>
node bridge-cli.cjs job list-capabilities
node bridge-cli.cjs job run <capability-id> [--input <json-file>] [--idempotency-key <key>] [--ttl <秒>] [--confirm] [--wait] [--timeout <秒>]
node bridge-cli.cjs job status <job-id>
```

注册表发生变化后，检查配置并重启后台桥；仅修改油猴脚本通常不需要重启桥。配对码短时且一次有效，不得写进源码或业务文件。

`job run` 的 `--input` 接受 JSON 文件路径，不接受内联 JavaScript。只有 capability 明确要求用户确认的写操作才使用 `--confirm`；该选项不能绕过 capability 自己的风险策略。`--ttl` 控制任务在没有 worker 时可等待多久，`--timeout` 只控制 CLI 等待多久，两者不是同一概念：CLI 超时退出后任务仍可能继续存在，应用 `job status` 按 ID 查询，不能立即盲目重建。

首个实时刷新示例：

```powershell
node bridge-cli.cjs job run lingxing.fba_shipments.refresh --wait
```

`lingxing.fba_shipments.refresh` 是 `read_only`，不接受输入，不要求确认；默认 TTL 600 秒、最大 TTL 3600 秒、lease 180 秒。成功 result 包含：

- `capability`、`worker_id`；
- `run_id`、`account_key`；
- `collected_at`、`bridge_committed_at`；
- `dataset_id`、`dataset_path`、`output_kind`；
- `source_record_count`、`record_count`、`summary`。

这些字段用于审计本轮运行，不替代正式数据。成功后仍需读取 `C:\数据\领星\manifest.json` 与其 `snapshot`，核对 `datasets.fba_shipments.state`、完成时间和记录数。

当前实现按单领星账号部署：`fba_shipments` 数据根、manifest 账号绑定和 worker 不包含任务级账号路由。不要让不同领星账号的多个浏览器 Profile 同时领取这个 capability。已有 manifest 会在落盘时拒绝账号不匹配并防止覆盖，但空目录首次绑定仍取决于先领取任务的在线 worker。若扩展多账号，必须把目标账号设为桥端校验的结构化字段，并为每个账号隔离 Dataset/目录和 worker 匹配；不得仅把账号字符串作为未校验 input 交给任意页面。

## 浏览器任务开发步骤

为现有采集插件增加 AI 主动刷新能力时，按以下顺序实施：

1. 先让手动运行稳定，确认页面请求、分页、完整性、桥 ACK 和落盘语义都已验证；
2. 定义窄而稳定的 capability ID，例如 `vendor.domain.resource.refresh`，不要命名为 `request`、`fetch_anything` 或 `run_script`；
3. 定义最小输入 schema。能从页面和已登记配置可靠得到的参数，不要交给 AI 任意传入；
4. 在注册表中登记 capability 及 create/read/execute ACL、风险等级、TTL、大小和确认策略；
5. 为正式业务插件增加 worker；不要给接口探针增加领取任务的能力；
6. 让 worker 把 capability 路由到同一 `runOnce`/采集函数，并增加跨标签或单飞锁；
7. 用 progress 报告阶段和续租，用 complete 报告小型摘要；完整数据照常写 Dataset/Artifact；
8. 将 capability 暴露到 catalog，并在业务说明中记录浏览器前提和正式结果位置；
9. 测试在线成功、浏览器未开、登录过期、接口失败、数据不完整、桥写入失败、执行进程消失和同幂等键重试；
10. 最后再允许 AI 使用 CLI 自动创建该任务。

接口探针只用于记录脱敏证据，绝不能被登记成通用任务执行器。否则等于把尚未审核的 endpoint 和 payload 变成远程调用面。

## 任务排错

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| `health` 失败 | 桥未启动、后台任务异常、端口冲突 | 先恢复桥，再创建任务 |
| 能力列表里没有目标 ID | 尚未登记、桥未重启、当前客户端无权限 | 检查 catalog/注册表和部署版本；不要换用任意 endpoint |
| 任务长期 `pending` | 浏览器或目标页面未打开、插件未启用/配对、电脑休眠 | 请用户打开已登录页面，确认插件在线；等待原任务或让其过期，避免重复创建 |
| CLI 等待超时但任务仍非终态 | `--timeout` 小于任务 TTL，或页面被浏览器节流 | 用原 job ID 查询；不要把 CLI 超时当任务失败 |
| 任务反复回到可领取状态 | worker 崩溃、页面刷新、lease 未续约 | 查看插件错误；确认耗时阶段持续 progress，保持幂等执行 |
| `failed` 且提示登录/transport | 登录失效，或不在能发现领星页面请求客户端的页面 | 用户重新登录并打开匹配页面后，再用新的幂等键重试 |
| `failed` 且提示完整性/桥 ACK | 分页位移、数据漏取、schema 变化或本地写入失败 | 保留旧成功数据，不推进基线；先修复采集链路 |
| FBA 错误 `LOGIN_REQUIRED` | 页面上找不到可用 `$post`，通常是未登录或页面尚未初始化 | 登录领星、打开 FBA 货件页面并刷新，再发起新任务 |
| FBA 错误 `WORKER_BUSY` | 手动、每日或另一浏览器任务正在共用采集锁 | 等原运行结束，查询原 job；不要并发刷新 |
| FBA 错误 `UNSUPPORTED_JOB_INPUT` | 给当前不接受参数的能力传了非空输入 | 去掉 `--input`；不能借输入改变 endpoint 或筛选范围 |
| FBA 错误 `BRIDGE_DELIVERY_FAILED` | 数据抓取可能完成，但 Dataset 未获得严格 ACK | 修复桥接/权限/落盘错误；旧成功 manifest 与基线应保持不动 |
| `CLAIM_LOST` / 任务再次被领取 | worker 没在 lease 内续约，或页面中途退出 | 不把旧 worker 的迟到结果标成任务成功；检查 progress 和运行幂等性 |
| `expired` | TTL 内没有 worker 完成 | 修复浏览器前提后创建新任务，不把过期任务当成功 |
| 任务 `succeeded` 但数据仍旧 | worker 结果语义错误或读错数据路径 | 核对 result、manifest、完成时间和记录数；这是实现缺陷，不能只看 HTTP 200 |

## AI 读取 FBA 数据

需要当前完整数据时：

1. 读取 `C:\数据\领星\manifest.json`；
2. 找到 `datasets.fba_shipments`；
3. 只有 `state` 为 `success` 时才视为完整可用；
4. 打开 `snapshot` 指向的文件；
5. 使用其中的 `records`，并用 `record_count` 核对数量。

需要最近变化时读取 `datasets.fba_shipments.last_change`：

- `export.kind = baseline` 表示首次比较基线，不代表本次全部新增；
- `export.kind = delta` 时使用 `export.changes`；
- `op = add`：完整新记录在 `current`；
- `op = update`：新记录在 `current`，差异在 `changed_fields` 或 `field_changes`；
- `op = remove`：旧记录在 `previous`。

不要修改或删除 manifest、快照与增量文件。状态失败或数据明显过旧时，应告诉用户数据尚未成功刷新。

## AI 发布配置

推荐流程：

1. 确认注册表中已有的配置 ID 和结构；
2. 从业务来源生成独立 JSON 文件；
3. 校验字段、类型、时间和来源；
4. 使用 `config publish` 发布；
5. 回读核对版本、更新时间和关键数量。

不要新建“万能配置”，也不要把密钥、Cookie 或登录令牌写入业务配置。新增配置时应同时定义用途、结构、生产者、消费者和最小权限。

## 既有 FBA 插件兼容规则

现有插件可以继续调用：

- `GET /health`
- `POST /v1/pair`
- `POST /v1/ingest`

FBA 的配对和数据提交继续使用 v1；新增的 `lingxing.fba_shipments.refresh` worker 使用 v2 job 接口，但沿用同一个已登记兼容客户端及令牌。其他新功能统一使用 v2，不要仿照 v1 配对。重构不得改变：

- FBA 数据仍落到 `C:\数据\领星\FBA数据`；
- 完整写入后才能更新成功 manifest；
- 快照、增量、数量、哈希和运行 ID 相互一致；
- 账号绑定与漏数保护仍由 FBA 适配器处理。

没有明确业务收益时，不必为了形式统一而迁移现有 FBA 插件。

## 明确禁止的设计

不要生成或建议以下能力：

- 接收任意 `C:\...` 路径并返回文件内容；
- 接收路径并任意写文件或覆盖目录；
- 从 HTTP 请求执行 JavaScript、PowerShell、CMD 或其他命令；
- 用 job 输入接受任意 URL、网站 endpoint、原始认证请求头、HTTP payload 或页面脚本；
- 把接口探针注册为通用 worker，或让一个 capability 动态路由到未审核的网页动作；
- 让所有客户端共享一个永久令牌；
- 在油猴源码、Git、日志或业务 JSON 中保存令牌；
- 让一个插件自动获得所有网站和所有资源权限；
- 绕过网站登录权限或把浏览器 Cookie 上传给桥；
- 在没有真实成功确认时声称数据已经落地。
- 在浏览器关闭、页面未登录或任务仍为 `pending` 时声称 AI 已实时拿到数据。

如果新需求似乎必须突破这些边界，应停止实现、解释风险，并设计更窄的专用资源或动作。

## 验收清单

- MCP 或现有能力的缺口已经明确；
- HAR 和日志中没有秘密进入源码或业务文件；
- 新资源有明确 schema、主键、完整性和失败语义；
- 客户端拥有独立 ID、来源白名单和最小权限；
- 注册表检查与相关自动化测试通过；
- 用户能完成安装、配对和首次运行；
- 网页端成功提示与桥端 ACK 一致；
- manifest、文件、记录数和时间均可核对；
- 数据已登记，后续智能体能够从 catalog 发现；
- 若支持主动刷新，capability 的 ACL、风险、TTL、lease、幂等和结果结构已经登记并测试；
- worker 只执行固定映射，手动与任务模式共用同一验证和落盘链路；
- 浏览器未开、登录失效、lease 到期和重复任务都能给出可诊断结果；
- 已回到最初业务任务并实际使用采集结果。
