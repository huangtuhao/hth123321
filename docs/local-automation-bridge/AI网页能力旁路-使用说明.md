# AI 网页能力旁路：使用说明

这份说明供 Codex、WorkBuddy 和其他智能体判断：当现有 MCP、正式 API 或已保存数据无法满足任务时，是否应该启用本地网页能力旁路。

它是任务路由和协作流程，不是桥的 API 手册。只有确定需要开发或修改浏览器客户端时，才继续阅读 [本地自动化桥-技术接入说明.md](本地自动化桥-技术接入说明.md)。

## 可放入智能体长期指令的触发规则

> 涉及网站数据或网站操作时，优先使用已有 MCP、正式 API 和已经登记的本地数据。如果所需数据、字段或操作不在现有能力范围内，不要直接判定任务无法完成；请检查 `C:\数据\业务自动化\catalog.json` 和“AI 网页能力旁路”说明。已有实时刷新 capability 时，通过 catalog 登记的 CLI 创建任务并等待结果；已有采集器但没有实时 capability 时，使用其最新成功数据，数据过期再请用户运行；完全没有采集能力时，向用户准确说明缺口，并请求最小必要的 HAR、页面位置或请求样本。随后按本地自动化桥技术说明生成最小权限的油猴插件，由用户在其已登录的浏览器中安装测试。数据打通后，继续完成最初任务，不要把“写出插件”当作任务终点。

这段规则适合常驻。后面的内容按触发后再读取，不需要每次任务全部加载。

## 什么时候触发

满足以下任一条件时，考虑旁路：

- MCP 或正式 API 没有所需的数据类型、字段、筛选方式或文件下载能力；
- MCP 能返回部分数据，但缺失会实质影响分析或后续功能；
- 任务必须在用户已经登录的网站页面中完成，而现有工具不支持该操作；
- `catalog.json` 已登记了相关数据或采集器，可以复用本地结果。
- `catalog.json` 已登记了对应浏览器任务 capability，可以在用户已登录页面在线时实时刷新。

以下情况不要立即新建旁路：

- 只是一次临时网络失败、参数错误或授权过期；应先诊断现有能力；
- MCP 已能完整、可靠地完成任务；
- 用户尚未授权会改变网站状态的操作；
- 需求要求绕过网站权限、上传 Cookie、共享账号令牌或开放任意本地路径。

旁路不是 MCP 的替代品，而是 MCP 能力边界之外的补充。

## 标准决策流程

### 1. 先明确真正缺少什么

不要只说“拿不到”。应记录：

- 原任务需要的数据或操作；
- 已尝试的 MCP、API 或本地数据；
- 缺少的具体资源、字段、时间范围、分页能力或网页动作；
- 该缺口为什么会阻止原任务。

如果现有能力只是调用失败，应先区分“能力不存在”和“能力暂时异常”。

### 2. 检查是否已有本地能力

先读取：

```text
C:\数据\业务自动化\catalog.json
```

按目录登记的信息检查 dataset、config、artifact 和相关说明，不要递归扫描整个 `C:\数据`。

- **已有可用数据集，时效满足任务**：按对应 manifest 或资源说明读取最新成功结果。
- **已有实时 capability，且确实需要更新**：使用 catalog 中的 CLI 创建任务并等待结果，再读取正式数据集。
- **已有采集器但没有实时 capability**：使用最新成功结果；数据过期时告诉用户需要在哪个页面手动运行，不要重复开发。
- **已有适配器但运行失败**：先排查现有链路，再决定是否修改。
- **没有相关能力**：进入新增浏览器适配器流程。

不要因为目录里存在一个新文件，就自行认定它是最新成功数据；以 manifest、版本信息或明确的成功确认作为依据。

## 已有 capability 时：由 AI 请求实时刷新

任务能力是这套旁路的优先实时入口。它让 AI 创建一个固定语义的任务，由已安装的正式油猴插件在用户当前登录页面中领取并执行。它不是让 AI 自由控制浏览器。

直接触发要求该 AI 运行环境能够读取本机 `catalog.json` 并执行本地 `node` 命令。只有文件读取能力、没有本地命令执行能力的智能体，仍可理解数据和说明，但不能自己创建任务；它应把下面的准确命令交给用户或有本地执行权限的工具，而不能声称已经刷新。

标准流程：

1. 从 `catalog.json` 读取实际 `cli_path`，不要猜安装目录；
2. 执行 `node <cli_path> job list-capabilities`，确认存在所需 capability；
3. 检查现有数据时间；只有任务确实需要更实时的数据时才刷新；
4. 执行 `job run` 并等待终态；
5. 成功后按该 capability 的说明读取对应 manifest 或正式数据文件，核对时间、记录数和完整状态；job result 本身不是业务数据；
6. 继续原分析任务。

首个能力示例：

```powershell
node <cli_path> job run lingxing.fba_shipments.refresh --wait
```

如果不使用 `--wait`，保存创建结果中的任务 ID，然后执行：

```powershell
node <cli_path> job status <job-id>
```

AI 不应把 `pending` 误报成成功。只有 `succeeded` 是成功终态；`failed` 和 `expired` 都应读取结构化错误并向用户说明下一步。长时间 `pending` 通常不是接口正在慢慢返回，而是没有在线 worker。

用户也可以在领星页面查看“领星自动化中心”状态条：收起时显示在线功能、运行中和异常数量，展开后显示已配对业务插件的状态。它适合判断“浏览器执行者是否在线”，但不是任务完成证明；最终仍以 job 终态和正式数据 manifest 为准。旧业务插件只有完成一次 runtime heartbeat 兼容更新后才会出现在这里。

对 `lingxing.fba_shipments.refresh`，成功后读取 `C:\数据\领星\manifest.json`，确认 `datasets.fba_shipments.state` 为 `success`，再读取其 `snapshot`；不要把 job result 或 `dataset_path` 当成货件记录数组。

浏览器侧必须满足以下前提：

- 浏览器正在运行，电脑未休眠；
- 安装并启用了对应的正式油猴插件；
- 匹配的网站页面已经打开且保持登录；
- 插件已和本地桥完成配对；
- 该插件被登记为 capability 的执行者。

当前 FBA 增量导出助手使用已登记的 v1 兼容客户端并自动兼容配对，用户不需要为 `lingxing.fba_shipments.refresh` 另输一次性配对码；新建的 v2 业务插件仍按各自说明配对。

当前 `fba_shipments` 目录和刷新 capability 按“一个桥实例对应一个领星账号”设计。触发刷新时不要同时让多个登录了不同领星账号的浏览器 Profile 运行该 FBA worker；先领取任务的 Profile 会执行。已有目录的账号绑定会阻止错误账号覆盖数据，但该任务会失败。若以后确实要并行管理多账号，应先增加明确的目标账号、隔离的数据目录和匹配规则，不能靠任意一个在线页面抢任务。

本地桥可以开机常驻，但不能代替浏览器登录，也不能主动启动或唤醒浏览器。页面最小化通常不影响能力语义，但浏览器节流、电脑休眠或页面被回收可能延迟领取。遇到这些前提不满足时，应请用户打开相应页面或重新登录，再重试一次；不要无限创建重复任务。

只有注册表中预先定义的 capability 才能运行。AI 不能通过任务输入指定任意 URL、领星 endpoint、原始请求 payload、JavaScript 或本地路径。如果列表中没有所需能力，进入探针和新适配器流程，而不是尝试把任意调用塞进已有 capability。

### 3. 没有适配器时，向用户索取最小必要信息

先向用户说明：现有 MCP 缺少什么，以及本地网页旁路为什么可能解决。通常按以下优先顺序索取信息：

1. 一次成功请求的 HAR；
2. 如果 HAR 不便提供，则提供目标页面、操作步骤和开发者工具中的请求/响应样本；
3. 数据量、分页上限、筛选条件和期望刷新频率；
4. 期望输出字段、文件类型或后续分析目标。

不要索取账号密码、Cookie、Auth Token 或浏览器本地存储中的秘密。HAR 可能包含敏感请求头，分析和保存时应避免复制、展示或写入源码。

### 4. 形成一个最小闭环

获得请求信息后，智能体应：

1. 分析接口、分页、稳定主键、返回结构和完整性条件；
2. 检查是否可以复用现有资源，不能复用时再设计专用 dataset、config 或 artifact；
3. 阅读技术接入说明、SDK 和油猴模板；
4. 生成权限最小、站点范围最小的油猴插件；如果需要由 AI 实时触发，再为其登记固定 capability；
5. 提供清楚的安装、配对、手动运行和任务 worker 说明；
6. 让用户在其已经登录的网站浏览器中测试；
7. 根据实际响应修正，直到桥确认接收且本地结果可验证。

首次开发通常需要用户参与安装和测试。桥不会把用户的网站登录态交给 AI，也不会让 AI 凭空知道一个网站的私有接口。

### 5. 回到原任务

打通采集不是最终目标。验证数据成功落地后，智能体必须：

1. 重新读取成功数据；
2. 核对记录数、时间、完整状态和关键字段；
3. 继续最初的分析、报表或自动化功能；
4. 说明本次数据来源和刷新时间；
5. 如果值得复用，把新资源登记到 catalog，使后续任务优先发现它。

## 向用户沟通的推荐格式

当 MCP 缺少能力时，可以这样说明：

> 当前领星 MCP 不提供“产品数据”资源，因此我无法仅通过 MCP 完成这部分。你的本地自动化桥可以作为旁路：由油猴插件在你已登录的领星页面调用对应接口，再把结构化结果保存到本地。我先检查是否已有相关采集器；如果没有，请提供一次该页面成功请求的 HAR。我会生成插件和测试步骤，数据打通后继续完成原来的产品分析。

这段说明应包含缺口、解决方向、需要用户提供的最小材料，以及“完成后继续原任务”的承诺。

## 示例：领星产品数据不在 MCP 中

1. WorkBuddy 尝试领星 MCP，确认产品数据资源不存在，而不是一次调用报错。
2. 读取 `catalog.json`，检查是否已有领星产品数据集或采集器。
3. 如果已有最新成功快照，直接用于分析。
4. 如果已有产品刷新 capability，AI 直接创建任务；如果只有旧采集器，再提示用户运行一次采集。
5. 如果完全没有，向用户索取产品页面 HAR 和期望字段。
6. 按技术接入说明生成领星产品采集油猴插件，并使用独立客户端和专用数据集。
7. 用户安装、配对并测试；智能体依据真实结果修正分页和字段映射。
8. 数据成功保存后，WorkBuddy 继续最初的产品分析。

## 能力边界

- 本地桥解决浏览器和本地工具之间的受控通信，不等于远程控制浏览器。
- AI 可以创建已登记 capability 的任务，但不能主动唤醒或登录浏览器，也不能调用未登记的网页动作。
- 新插件仍由用户安装并配对；只有明确实现并登记了 worker 的功能，才能由 AI 主动创建任务。
- 网站登录权限仍由用户和网站决定；不得绕过账号权限。
- 影响网站数据的写操作必须单独登记风险、要求显式确认并获得用户授权；不能沿用只读刷新能力的自动执行策略。
- 如果智能体无法访问本机文件，应让用户附加这份说明及技术文档，或使用具备本机文件权限的执行环境。

## 进入技术实现

只有在以下情况才继续读取 [本地自动化桥-技术接入说明.md](本地自动化桥-技术接入说明.md)：

- 需要生成或修改油猴客户端；
- 需要登记 dataset、config、artifact 或客户端权限；
- 需要新增或修改浏览器任务 capability、输入结构、执行客户端或确认策略；
- 需要发布配置、生成配对码或排查桥接错误；
- 需要验证现有 FBA 兼容链路。

技术实现前还应读取 `catalog.json` 中登记的 `registry_path`、`sdk_path` 和 `examples.userscript_template`，不要假定模块安装路径。
